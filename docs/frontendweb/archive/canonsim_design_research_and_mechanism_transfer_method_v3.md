# CanonSim — Design Research & Mechanism Transfer Method v3

**Date:** 2026-09-29  
**Status:** RESEARCH / PROPOSAL  
**Authority:** Non-binding until adopted through the existing CanonSim owner-gated documentation path.  
**Role:** Methodological adapter for design research, reference analysis, mechanism transfer, visual validation, and agent-facing design decisions.  
**Scope:** CanonSim frontend/web-agent work and other visual/interface tasks where external references materially influence design decisions.  
**Primary integration target:** `CANONSIM_FRONTEND_WEB_AGENT_PACK_FINAL_v1_3`  

> **Core rule:** Refero-derived method improves how CanonSim researches, transfers, and validates design mechanisms. It does not define CanonSim product law, visual identity, runtime semantics, architecture, or proof authority.

---

## 0. Executive doctrine

CanonSim already owns the product. Existing CanonSim owner documents define interaction law, visual grammar, application/runtime semantics, Observatory semantics, world presentation, proof, and repository routing.

This document exists only to make a recurring agent problem explicit:

```text
external references
→ observation
→ mechanism extraction
→ transfer boundary
→ CanonSim invariant
→ native adaptation
→ target envelope
→ implementation
→ falsifiable proof
```

The transferable asset is therefore **method**, not appearance.

### 0.1 One-line doctrine

```text
RESEARCH LIKE A DESIGNER,
TRANSFER LIKE A SYSTEM ARCHITECT,
LOCK INVARIANTS BEFORE BUILDING,
PROVE THE RESULT AFTERWARD,
AND NEVER LET THE DONOR BECOME CANONSIM AUTHORITY.
```

### 0.2 Canonical relationship

```text
CANONSIM
    = product authority
    = semantic authority
    = visual identity
    = runtime/application authority
    = repository ownership
    = proof ownership

REFERO-DERIVED METHOD
    = research discipline
    = observation/interpretation separation
    = mechanism extraction
    = transfer-boundary discipline
    = target-envelope discipline
    = falsifiable design validation
```

### 0.3 Non-negotiable boundary

A donor reference, screenshot, website, design system, framework, or external design methodology may inform a CanonSim decision.

It may not silently become:

```text

```

Any durable CanonSim rule produced by research must be routed through the existing owner-gated documentation path.

## 1.1 Source precedence

For design/frontend work, use this precedence:

```text
1. AGENTS.md and repository invariants
2. Current active-repository owner laws / accepted contracts
3. Owner-gated CanonSim decisions and task rows
4. Existing accepted implementation and tests
5. Approved CanonSim reference targets
6. CanonSim research evidence

8. External references
9. Agent taste, model memory, generic design convention
```

External research can propose or falsify a decision. It cannot override an active owner.

# 2. What this method transfers

The portable unit is:

```text
SOURCE OBSERVATION
    ↓
MECHANISM
    ↓
FUNCTION / PROBLEM SOLVED
    ↓
TRANSFER BOUNDARY
    ↓
CANONSIM INVARIANT
    ↓
NATIVE CARRIER
    ↓
ADAPTATION
    ↓
TARGET ENVELOPE
    ↓

    ↓
FALSIFIER / PROOF
```

The portable unit is **not**:

```text

palette
page anatomy
component shape
framework structure
marketing hierarchy
brand ornament
copy tone
web navigation defaults
```

Aesthetic similarity can be an outcome. It is never the transferable specification by itself.

## 2.1 Five core mechanisms

The Refero-derived material is deliberately reduced to five mechanisms that materially improve the CanonSim agent workflow:

1. **Observation / interpretation separation**
2. **Mechanism extraction instead of appearance copying**
3. **Explicit transfer boundaries**
4. **Target Envelope instead of screenshot worship**
5. **Claim → Falsifier → Evidence validation**

These mechanisms are sufficient for most CanonSim frontend research. More elaborate research rituals are conditional, not default.

# 3. Research depth is risk-based

Research is not a ritual required for every CSS, component, or copy adjustment.

## 3.1 Direct build

Use when an approved CanonSim target already exists and the change is local and bounded.

```text
confirm owner
→ confirm approved target
→ make smallest justified change
→ focused proof
```

No new external research is required unless a real design fork appears.

## 3.2 Light research

Use when a decision is under-specified but the design space is narrow.

```text
identify gap
→ inspect small contrast set
→ extract one/few mechanisms
→ bind to existing law
→ focused proof
```

## 3.3 Standard research

Use for a new surface, reusable interaction pattern, significant visual change, or material information-architecture choice.

```text
task + semantics + platform
→ targeted research
→ mechanism synthesis
→ transfer record
→ target + invariants
→ implementation
→ proof
```

## 3.4 Deep research

Use when the choice is ambiguous, cross-cutting, highly visible, reusable, architecture-sensitive, or difficult to reverse.

```text
multiple relevant research angles
→ strong + contrasting references
→ explicit tradeoffs
→ transfer boundaries
→ accessibility / localization / epistemic review
→ performance implications
→ target envelope
→ implementation evidence
→ claim-bound challenge
```

## 3.5 Research depth equation

Depth is selected from:

```text
ambiguity
+ consequence of a wrong choice
+ reuse scope
+ semantic sensitivity
+ platform sensitivity
+ reversibility
```

Search count is not evidence quality.

Do not perform research merely to satisfy a numeric quota.

# 4. Research dimensions

Research dimensions are investigation axes, not product surfaces.

## 4.1 STYLE

Investigate:

```text
hierarchy

density
typography roles

motion register
```

## 4.2 SCREEN

Investigate:

```text
information priority
selection
state presentation
forms
tables
inspectors
empty/loading/error states
disclosure
density management
```

## 4.3 FLOW

Investigate:

```text
entry
choice
system response
confirmation
failure
recovery
state restoration
confidence / uncertainty handling
```

## 4.4 PLATFORM / ENVIRONMENT

Especially important when donor references are web-oriented but CanonSim targets desktop/local tooling or a browser frontend with CanonSim-specific runtime constraints.

Verify as applicable:

```text
native desktop conventions
browser constraints
DPI / scaling
keyboard / focus
window / viewport behaviour
multi-tab behaviour
local/offline operation
long-running operations
local inference / shared-resource constraints
filesystem / asset constraints
performance and boundedness
```

The question is not:

```text
"Does this look good on the donor platform?"
```

The question is:

```text
"Does the underlying mechanism remain valid under CanonSim semantics,
platform constraints, and proof requirements?"
```

## 4.5 Dimension selection

Do not force a fixed sequence such as `STYLE → SCREEN → FLOW`.

First determine:

```text
TASK
SEMANTIC STATE / AUTHORITY
PLATFORM
RISK
```

Then select only the dimensions needed.

Examples:

```text
single control refinement      → SCREEN + PLATFORM
visual identity direction      → STYLE + PLATFORM
configuration workflow         → SCREEN + FLOW + PLATFORM
Observatory research surface   → SCREEN + FLOW + PLATFORM + epistemic constraints
world presentation mechanism   → STYLE + PLATFORM + WORLD owner constraints
```

# 5. Source acquisition and admission

## 5.1 Source classes

A research note MUST distinguish:

```text
SOURCE FACT
    directly supported by the source/artifact

TRANSFER
    mechanism deliberately adapted from the source

CANONSIM PROPOSAL
    new CanonSim rule, non-binding until adopted

INFERENCE
    reasoned interpretation not directly stated by the source

DEFERRED / UNKNOWN
    insufficient evidence
```

Do not silently promote an inference into a requirement.

## 5.2 Source admission record

For a material external source, record at minimum:

```text
source identity
source type
source location / screen / file where practical
licence / redistribution relevance when applicable
what was directly observed
what mechanism is claimed
what remains unknown
```

For code/assets, existing CanonSim reference and licence rules remain authoritative.

## 5.3 Anti-averaging rule

Do not construct a generic centroid from multiple references.

Prefer:

```text
PRIMARY REFERENCE
    → overall direction / structure / density

SECONDARY REFERENCES
    → bounded mechanisms only

CANONSIM
    → semantic + platform adaptation
```

One dominant direction should remain legible.

A hybrid is acceptable only when its constituent mechanisms have separate reasons to coexist.

# 6. Observation before interpretation

Before saying a reference is “better”, “cleaner”, “premium”, “modern”, or “more usable”, extract the observable evidence.

## 6.1 Observation template

```text
OBSERVATION
    What can be directly seen or measured?

INTERPRETATION
    What mechanism may explain the observation?

FUNCTION
    What user/system problem appears to be solved?

CONFIDENCE
    FACT | INFERENCE | UNKNOWN
```

Examples of weak notes:

```text
"This feels cleaner."
"The dashboard is more premium."
"The cards are easier."
```

Examples of useful notes:

```text
"Primary actions remain in a stable region across three tested states."
"Secondary metadata is visually subordinate to the task result."
"Selection changes both outline and text emphasis, so state is not colour-only."
```

Adjectives can describe preference. They are not evidence by themselves.

# 7. Mechanism extraction

For every material donor pattern, answer:

```text
WHAT happens?
WHY does it work in the donor?
WHAT problem does it solve?
WHICH mechanism produces the effect?
WHICH donor assumptions are non-portable?
WHICH CanonSim invariant should survive?
WHICH existing owner/carrier should implement it?
WHAT changes under CanonSim platform and semantics?
HOW can transfer success be falsified?
```

## 7.1 Mechanism test

A mechanism candidate is admissible only when another agent could implement or falsify the claim from the transfer record.

If the record still depends on:

```text
"it looks good"
"it feels premium"
"users will like it"
"this is modern"
```

the research is incomplete.

## 7.2 Native carrier principle

Prefer an existing CanonSim primitive or owner as the carrier:

```text
existing surface
existing view
existing container
existing state grammar
existing token
existing proof path
existing application contract
```

External research must not create a new abstraction simply because the donor has one.

# 8. Transfer Boundary

Every material mechanism transfer should state what **stops at the donor boundary**.

Example:

```text
DONOR MECHANISM
    persistent context strip keeps identity visible during navigation

TRANSFERRED
    persistent context identity remains visible during analytical navigation

TRANSFER BOUNDARY
    donor's navigation model, labels, styling, routing, and framework
    are not transferred

CANONSIM CARRIER
    existing Observatory context strip contract
```

This prevents the common failure mode:

```text
donor mechanism
→ donor assumptions
→ donor implementation
→ donor vocabulary
→ donor architecture
```

Only the justified mechanism crosses the boundary.

# 9. Target Envelope

A screenshot, mockup, or reference frame is an exemplar. It is not automatically a pixel-perfect production command.

## 9.1 Three levels

```text
REFERENCE DIRECTION
    intended visual behaviour / relationship

REFERENCE TARGET
    concrete approved exemplar / frame / mockup

TARGET ENVELOPE
    invariants that must remain true across valid runtime conditions
```

## 9.2 Target envelope contents

A material visual decision should separate:

```text
MUST PRESERVE
    hierarchy
    density relationship
    semantic accent role
    state visibility
    selection/focus treatment
    interaction ownership
    epistemic distinctions

MAY VARY
    text length
    item count
    dynamic data
    exact geometry under DPI/localization
    runtime-only content
    supported viewport adaptation
```

## 9.3 Why this matters for CanonSim web frontend

The web implementation must survive:

```text
Cyrillic
long labels
German-like compound words
variable data
loading / stale / failure states
multiple tabs
supported viewport changes
accessibility modes
runtime identity changes
```

An implementation that matches one screenshot while failing these conditions has not satisfied the target envelope.

## 9.4 Target envelope is stronger than screenshot equality

Visual proof should compare against the invariant envelope, not blindly against pixels.

Acceptable variation may result from:

```text
localization
DPI / scaling
content length
dynamic state
supported viewport class
native platform convention
```

Unacceptable variation is any change that breaks an explicitly locked invariant.

# 10. Reference Lock

Reference Lock is a **row-local commitment**, not a global design authority.

Use it when a task has a material external or first-party visual direction.

```text
PRIMARY DIRECTION
    one dominant direction / approved first-party target

PRESERVE
    3–5 essential mechanisms / relationships

BORROW ONLY
    bounded secondary mechanisms

ROLE RULES
    semantic role of every borrowed mechanism

REJECT
    explicit donor assumptions / anti-patterns

CANONSIM INVARIANTS
    semantic + interaction + identity constraints
```

Do not create a permanent Reference Lock registry unless a separate owner explicitly adopts one.

# 11. CanonSim epistemic preservation

This method must never blur CanonSim's epistemic distinctions.

## 11.1 Independent axes

Where applicable, preserve separate:

```text
AUTHORITY
    CANONICAL | OBSERVED | DERIVED | UNKNOWN

CLAIM
    FACT | INFERENCE | HYPOTHESIS | PROPOSAL | UNKNOWN
```

The exact vocabulary remains owned by the applicable CanonSim law.

## 11.2 Visual emphasis is not semantic authority

Visual treatment may communicate:

```text
priority
focus
selection
interaction affordance
attention
```

It must not silently manufacture:

```text
canonicality
observed status
claim certainty
causal conclusion
knowledge scope
```

A stronger colour, thicker line, larger node, animation, or spatial position does not create evidence.

## 11.3 Negative states remain distinguishable

When relevant to a decision, do not collapse:

```text
UNKNOWN
NOT OBSERVED
NO MATCH
NO EVIDENCE
ABSENT
OUT OF SCOPE
FAILED
STALE
BLOCKED
UNAVAILABLE
CONFLICT
```

into a generic “nothing”, “error”, or empty state.

## 11.4 Canonical visual rule

```text
visual system
    = projection of permitted semantic/read-side information

never
    = a second source of truth
```

Generated art, decorative texture, causal-looking lines, and visual prominence cannot create semantic truth.

# 12. Progressive disclosure and semantic density

Borrow the principle of progressive disclosure only as an information rule:

```text
USER QUESTION
    → RELEVANT DISTINCTION
    → MINIMUM SUFFICIENT INFORMATION
    → DEEPER DETAIL ON DEMAND
```

Do not expose every backend property merely because it exists.

For analytical surfaces, preserve the established CanonSim grammar:

```text
QUESTION
→ SCOPE
→ FOCUS
→ PRIMARY VIEW
→ CONTEXT
→ INSPECT / COMPARE / DRILL
→ EVIDENCE
→ PROVENANCE
→ NEXT DISCRIMINATOR
```

## 12.1 Attention is a budget

Treat these as interacting resources:

```text
semantic density
interaction density
annotation density
motion density
material/detail density
```

High visual detail is not automatically high quality.

Detail is justified by:

```text
ambiguity
+ decision cost
+ causal leverage
+ identity value
```

## 12.2 Semantic LOD remains authoritative

Use disclosure to reduce cognitive load:

```text
MACRO → MESO → MICRO → INSPECT
```

Do not turn UI progressive disclosure into an excuse to expose a backend-scale object universe.

# 13. Motion transfer

Motion is a communication channel, not default decoration.

## 13.1 Motion record

For every non-trivial motion define, where applicable:

```text
purpose
trigger
duration class / token
easing
allowed properties
static equivalent
reduced-motion behaviour
performance implication
```

Concrete timings and runtime rules remain owned by the CanonSim visual/runtime owners.

## 13.2 Valid motion functions

```text
selection change   → focus / selection transition
result arrival     → bounded data-arrival cue
state change       → transition exposing new state
comparison change  → before/after registration
causal inspection  → local causal emphasis
```

Invalid default uses:

```text
continuous glow
unbounded particles
all cards flying in
idle motion with no communication role
```

## 13.3 Motion invariant

```text
EVERY NON-TRIVIAL MOTION
→ HAS A PURPOSE
→ HAS A STATIC EQUIVALENT
→ HAS A REDUCED-MOTION PATH
```

Motion must never become the only carrier of a consequential state.

# 16. Performance-aware visual decisions

For any material mechanism, evaluate:

```text
SEMANTIC VALUE
VISUAL COST
INTERACTION COST
RUNTIME COST
MAINTENANCE COST
```

Then choose:

```text
KEEP | MODIFY | BOUND | DEFER | REMOVE
```

A visual mechanism is not “bounded” merely because it appears lightweight.

Boundedness requires:

```text
declared ceiling
+ measurement
+ degradation path
```

Concrete performance budgets and benchmark ceilings remain in the applicable CanonSim owner documents and web-agent contracts.

Do not duplicate numerical budgets here.

# 17. Anti-AI-slop mechanism test

External references should prevent generic convergence, not cause generic convergence by averaging.

Be suspicious of choices that survive only because they are familiar model defaults:

```text
card wrapper by default
second accent by default
gradient decoration
glow without semantic role
generic symmetry
ornamental depth
texture as filler
AI-default typography
reference averaging
```

## 17.1 CanonSim questions

For each non-trivial visual choice ask:

```text
What real CanonSim product/world property motivates this?
What user/system problem does it solve?
Which CanonSim invariant does it express?
Would the identity survive if the decoration were removed?
Is colour carrying a defined semantic role?
Does motion communicate a real state/change?
Did the donor's distinctive mechanism survive?
Did the agent normalize the design toward generic conventions?
```

## 17.2 No novelty quota

Do not impose:

```text
one memorable detail
one experimental element
one unusual shape
one special effect
```

as mandatory acceptance criteria.

A new signature mechanism is justified only when it carries identifiable semantic, interactional, or identity value and survives the applicable CanonSim admission tests.

# 18. Claim → Falsifier → Evidence

A material design proposition should, where practical, be expressed as:

```text
CLAIM
    ↓
FALSIFIER
    ↓
EVIDENCE
    ↓
DISPOSITION
```

Example:

```text
CLAIM
    A restrained accent hierarchy keeps primary actions discoverable in a dense expert surface.

FALSIFIER
    In a supported task state, the user cannot identify the primary action
    without colour-only interpretation or unnecessary exploration.

EVIDENCE
    runtime capture + task proof + accessibility inspection

DISPOSITION
    KEEP | MODIFY | REJECT
```

A visual preference that cannot be meaningfully challenged remains a preference, not a verified design claim.

## 18.1 Evidence classes

Keep distinct:

```text
STATIC PROOF
    tokens, structural contracts, forbidden values, metadata

RUNTIME PROOF
    layout, focus, interaction, state rendering, motion, scaling

TASK / HUMAN PROOF
    task completion, recovery, recognition, unnecessary effort

PERFORMANCE PROOF
    frame time, resource, latency or boundedness evidence when material
```

One evidence class cannot impersonate another.

For the web pack, preserve its existing proof vocabulary instead of creating a competing proof framework.

# 19. Visual QA

For a material visual change:

```text
SOURCE TRUTH
    approved target / row-local Reference Lock / Target Envelope

IMPLEMENTATION EVIDENCE
    runtime capture / recorded state / test artifact

CONTEXT
    viewport + surface + state + locale/DPI as relevant

FINDINGS
    semantic / interaction / visual / accessibility / performance

DISPOSITION
    PASSED / BLOCKED / MODIFY / REJECT
```

## 19.1 Visual defect classification

When a visual-specific severity is useful, use:

```text
VIS-0  blocks truthful or usable rendering / reveals semantic falsehood
VIS-1  material task/state/identity/accessibility defect
VIS-2  noticeable visual/interaction degradation
VIS-3  polish / non-critical refinement
```

These labels do not replace CanonSim project priorities such as P0–P4 where those already exist.

## 19.2 Screenshot is evidence, not truth

A screenshot can show:

```text
what was rendered
under a particular state
at a particular viewport / locale / revision
```

It cannot by itself prove:

```text
semantic authority
backend correctness
effective-state correctness
causal truth
general usability
performance under other states
```

# 20. Claim-bound mutation testing

Mutation testing is useful only when it attacks a specific design claim.

Use:

```text
CLAIM
    ↓
CONTROLLED VISUAL MUTATION
    ↓
EXPECTED CONSEQUENCE
    ↓
OBSERVATION
    ↓
DISPOSITION
```

Examples:

```text
accent hierarchy claim
→ reduce accent on non-actions
→ verify primary-action distinction survives

state-visibility claim
→ remove colour cue
→ verify non-colour state channel remains usable

density claim
→ compress spacing within supported range
→ verify hierarchy remains recoverable

identity claim
→ remove ornamental texture
→ verify signature grammar remains recognizable
```

Do not introduce arbitrary mutation quotas.

---

# 21. Held-out transfer

Held-out transfer is conditional.

Use it when the claim concerns generalization:

```text
STYLE / MECHANISM
    → unseen content / state / density / environment
    → verify invariant survives
```

Do not make held-out testing a mandatory ritual for every frontend task.

---

# 22. Minimal visual witness

When a visual dispute is hard to interpret:

```text
full scene / surface
→ remove irrelevant material
→ preserve the disputed mechanism
→ smallest useful witness
→ identify violated invariant
→ repair
→ retest
```

The purpose is causal legibility, not presentation polish.

Use this when agent output contains enough UI that the actual failure mechanism is difficult to isolate.

---

# 23. New surface / component / abstraction gate

External references do not justify abstraction by themselves.

Before adding a surface/view/component/registry, ask:

```text
Does an existing task need this?
Does an existing surface already own the task?
Can an existing view/container carry the mechanism?
What distinct state/lifecycle/consumer justifies the abstraction?
Which owner carries it?
What falsifier would show the abstraction is unnecessary?
```

If the only answer is:

```text
"the reference has one"
```

reject the abstraction.

This rule is especially important for agent-generated React architectures where donor component structures can otherwise become accidental product architecture.

---

# 24. Surface, view, container discipline

CanonSim retains:

```text
SURFACE
    = user intent / work context

VIEW
    = representation

CONTAINER
    = semantic region inside a surface
```

Therefore:

```text
reference ≠ new surface
reference ≠ new view
reference ≠ new component
reference ≠ new abstraction
```

Use the smallest native carrier that satisfies the task and target envelope.

```text
browser-side execution engine
second event bus
second state authority
second proof system
```

The web implementation remains subordinate to active CanonSim ownership and gateway/application contracts.

# 26. Agent procedure

For every substantial visual/frontend/design task:

```text
1. Identify the active owner and task.
2. Identify the user task.
3. Identify the authoritative semantic state.
4. Identify the owning surface and existing representation.
5. Identify platform/runtime constraints.
6. Check whether an approved target already exists.
7. If yes, prefer direct bounded build.
8. If no, select minimum research depth by risk.
9. Select only the needed research dimensions.
10. Acquire admissible references.
11. Separate observation from interpretation.
12. Extract mechanisms, not appearances.
13. State the transfer boundary.
14. Identify the CanonSim invariant.
15. Identify the native carrier/owner.
16. Establish a row-local Reference Lock / Target Envelope when material.
17. Check accessibility, localization, state, motion and performance implications.
18. Implement through existing architecture.
19. Capture implementation evidence.
20. Compare against the Target Envelope.
21. Run static/runtime/task/performance proof as applicable.
22. Run claim-bound mutation when it materially challenges the decision.
23. Run held-out transfer only when generalization is the actual claim.
24. Classify visual findings with VIS-0..VIS-3 when useful.
25. Keep / modify / reject the mechanism.
26. Route only durable CanonSim residue into the existing owner document.
```

# 27. Required research / transfer record

For a material transfer, use a compact structured record.

```text
TASK
    user/system problem being solved

OWNER
    CanonSim document / active contract

SOURCE
    exact source + screen/page/file where practical

SOURCE TYPE
    STYLE | SCREEN | FLOW | ASSET | PLATFORM

OBSERVATION
    directly observed fact

MECHANISM
    rule producing the observed effect

FUNCTION
    user/system problem solved in donor

TRANSFER BOUNDARY
    donor assumptions that MUST NOT cross into CanonSim

CANONSIM INVARIANT
    property that must survive adaptation

NATIVE CARRIER
    existing CanonSim owner / primitive / surface / contract

ADAPTATION
    CanonSim semantic/platform changes

TARGET ENVELOPE
    what must be preserved vs what may vary

COST / RISK
    semantic · UX · accessibility · localization · performance · maintenance

FALSIFIER
    observation that would show the transfer is wrong

PROOF
    static · runtime · task · performance evidence as applicable

DISPOSITION
    KEEP | MODIFY | BOUND | DEFER | REJECT

DURABLE RESIDUE ROUTING
    exact CanonSim owner to update, if any
```

A record is useful only when another agent could implement or falsify the claim from it.

Do not write long narrative when this structure is sufficient.

# 28. Anti-cargo-cult gate

Before admitting any donor concept, ask:

```text
What CanonSim failure does it prevent or what task does it improve?
What existing owner already carries most of it?
What is the minimum useful form?
What is the transfer boundary?
What CanonSim invariant does it preserve?
What disappears when the donor disappears?
What evidence demonstrates value?
```

Reject or defer a transplant that requires a new:

```text
global authority
persistent store
generic graph
universal component framework
workflow engine
semantic registry
parallel asset manifest
parallel proof system
```

unless an independent CanonSim consumer and owner-gated decision justify it.

# 29. CanonSim visual identity boundary

External methodology must not replace CanonSim's first-party identity.

The visual system remains responsible for its own grammar, including where applicable:

```text
Workbench chrome
    quiet / precise / instrument-like / high legibility

World presentation
    distinctive / graphic / material / deterministic / semantically bounded
```

Shared grammar may include:

```text
typographic logic
spacing logic
selection/focus grammar
semantic status grammar
information hierarchy
```

Shared grammar does not imply shared ornament.

Reject drift toward:

```text
generic fantasy UI
ornate medieval UI
parchment cosplay
cinematic game HUD
photorealistic GIS defaults
generic SaaS dashboarding
AI-default card grids
unbounded effects
AI-generated world truth
```

These are anti-drift guardrails, not a replacement for the actual CanonSim visual owner.

# 33. Non-negotiable invariants

```text
1. CanonSim defines the product.
2. CanonSim owners define product law.
3. Refero-derived method is methodology, not authority.
4. Owner law overrides external design research.
5. Research is required only when the decision warrants it.
6. Research depth scales with risk and ambiguity, not query quotas.
7. Research dimensions are STYLE / SCREEN / FLOW / PLATFORM.
8. Select only the dimensions needed for the task.
9. Observation is separate from interpretation.
10. References provide mechanisms, not authority.
11. Never average references into a generic visual centroid.
12. Prefer one dominant direction; secondary references stay bounded.
13. Every material transfer identifies a TRANSFER BOUNDARY.
14. Every material transfer identifies a CANONSIM INVARIANT.
15. Existing CanonSim owners are the preferred native carriers.
16. Reference Lock is row-local, not global authority.
17. Screenshots are exemplars; TARGET ENVELOPE defines production invariants.
18. Surface count follows user intent and ownership, not reference count.
19. External research never creates a new abstraction by itself.
20. AUTHORITY and CLAIM remain distinct semantic axes where applicable.
21. Visual emphasis must not manufacture semantic authority.
22. Decision-relevant negative states remain distinguishable.
23. Generated media never becomes semantic truth.
24. Motion is a semantic channel; non-trivial motion needs purpose, static equivalent, and reduced-motion path.
25. Asset design intent and asset runtime identity remain separate.
26. Performance is considered before material visual commitment; concrete budgets stay with existing owners.
27. Anti-slop questions must identify a real product/system reason for non-trivial choices.
28. No novelty quota is required.
29. Mutation tests are claim-bound, not ritual.
30. Held-out transfer is conditional on a generalization claim.
31. Static, runtime, task, visual, and performance proof remain distinguishable.
32. Visual QA compares against the target envelope, not blind pixel identity.
33. VIS-0..VIS-3 are visual classifications only; they do not replace project priorities.
34. Research does not equal adoption.
35. Durable residue routes into existing owner documents.
36. New infrastructure requires a concrete failure/task, owner, consumer, and falsifiable value proposition.
```
