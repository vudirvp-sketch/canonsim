## A. Исследование выполнено ДО решения (не вслепую)

### A.1 Метод

Полнорепозиторный скан цитируемости: каждая из 31 строк DECISIONS
развёрнута в полное семейство ID (компаунд-формы `D-001/D-009` и
диапазоны `D-065..D-082`), затем каждый ID искался во ВСЕХ текстовых
файлах репо (.md / .py / .ts / .tsx / .json / .bat / .yaml / .toml /
.txt / .gbnf), сам `docs/DECISIONS.md` исключён — считаются только
внешние цитаты. Инструмент: одноразовый скрипт сессии (вне репо,
Правило 9).

### A.2 Вердикт: ВСЕ 31 СТРОКИ ЖИВЫЕ — ноль полностью мёртвых

| Показатель | Значение |
|---|---|
| Строк с нулём внешних цитат | **0 из 31** |
| Минимум цитат на строку | 6 (D-248/D-249 — и те живые: NAV, отчёты) |
| Медиана | 20+ внешних ссылок на строку |
| Redot-строка (D-244/D-245) | **30 цитат**, см. ниже |

Каждая строка — либо живой закон (цитируется кодом/тестами/доками),
либо живая история с работающими ссылками. «Точно старое и ненужное»
на уровне СТРОК не существует.

### A.3 Redot-строка — разбор отдельно (ваша примерная кандидатура)

D-244/D-245 несёт **30 внешних цитат**: `README.md`,
`docs/AGENT_NAVIGATION.md`, `docs/CONTRACTS.md`,
`docs/FRONTEND_WEB_LAW.md`, `docs/WORKBENCH_APP_LAW.md`,
`docs/WORLD_PRESENTATION_LAW.md`, `docs/SSI_TOPOLOGY.md`, STATUS FAQ,
TASKS, `frontend/package.json`, `scripts/workbench_launch.py`,
`docs/frontendweb/FRONTEND_WEB_AGENT_CONTEXT.md`, отчёты итераций. Это
не исторические упоминания — это **действующий авторитет**: «frontend/
— АКТИВНЫЙ веб-клиент (D-244)», «редот-половина УДАЛЕНА (D-245)»,
«вопрос по Redot/Godot → в архивный пак (D-245)». Удаление строки =
30 порванных цитат + потеря authority-записи о текущем стеке.

Её объём (7.7 КБ) — не раздувание, а доказательная запись: R4-PCC
(шесть полей, закон §2.9/SSI-N017) + четыре SSI-N020 GC-карточки
удаления, которые коллапс iter-310 **намеренно сохранил полностью**
(отчёт iter-310 §A.2 п.5: «компаунд-PCC-записи всех R3+/R4 строк …
все семь карточек удаления SSI-N020 … сохранено полностью»). Сжимать
их дальше = резать субстанцию против §6.1 и против собственного
решения iter-310.

### A.4 Почему вторая ветка (капа 35), а не коллапс-слияние

1. Число 30 родилось в эпоху iter-7 со строками по ~300 байт; сегодняшние
   семейства — 1–11 КБ компаунд-ID. По записям субстанция в измерении
   «записей» выросла на порядок — при этом байтовый закон (D-024-сжатие
   + §6.1 never-cut) уже охраняет реальное раздувание.
2. §6.1 прямо предписывает: субстанция не режется под капу — капа
   поднимается с записанным обоснованием. Ровно это и сделано.
3. Коллапс-слияние соседних семей ради «−1 строка» дало бы мега-строку
   D-242..D-251 (~14 КБ) — хуже по байтовому закону, и через ~50
   итераций та же проблема вернулась бы.
4. Темп: после коллапса iter-310 (40→30) за 58 итераций добавилась
   ровно одна новая строка (D-250; D-251 легла в семейство). Очередь
   (M6-вердикты, форма фикса KI#120, measured-wall-приёмки) называет
   свежие строки — 35 даёт честный запас без разоружения стража.
